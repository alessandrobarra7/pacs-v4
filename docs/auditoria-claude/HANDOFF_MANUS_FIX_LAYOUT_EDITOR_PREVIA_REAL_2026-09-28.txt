3. MECANISMO DO PROBLEMA 1 (o mais grave): "Prévia real" colapsando
------------------------------------------------------------------------------

A tela tem dois modos reais, alternados por dois <button>: "Editar blocos" e
"Previa real". Os dois renderizam o mesmo <SharedReportSheet /> com os mesmos
dados de exemplo (REAL_PREVIEW_SAMPLE), positions, logos, pageSize e margens
— a diferença deveria ser só a camada de interação (arrastar/redimensionar),
que só aparece em "Editar blocos".

No modo "Editar blocos", o SharedReportSheet fica dentro de:

    <div ref={canvasRef} style={{ ...getCanvasOuterStyle(effectiveLayoutPrefs.pageSize), ... }}>
      <SharedReportSheet ... style={{ width: "100%", height: "100%" }} />
      ...camada de interação...
    </div>

`getCanvasOuterStyle()` (client/src/lib/layoutEditorAreaUtil.ts) devolve:

    { width: "100%", maxWidth: `${widthMm}mm`, aspectRatio: `${widthMm} / ${heightMm}` }

O `aspectRatio` é o que dá ao navegador uma forma de resolver a largura de
forma determinística mesmo dentro de um flex item sem largura própria — o
`canvasRef` acaba herdando `maxWidth` (210mm/216mm conforme A4/Letter) como
sua largura real, porque o par width:100%+aspectRatio força o algoritmo de
sizing do flexbox a tratar a largura como definida.

No modo "Previa real" (antes da correção), o SharedReportSheet ficava
DIRETO dentro do container flex externo, sem nenhum wrapper equivalente:

    <SharedReportSheet ... style={{ width: "100%", maxWidth: `${paperWidthMmValue}mm`, minHeight: `${paperHeightMmValue}mm` }} />

Sem `aspectRatio` (nem qualquer outro mecanismo de largura definida) em
NENHUM ancestral entre o componente e o container flex externo (que por sua
vez também não tem largura própria — é `<div>{tabs}{sheet}</div>` dentro de
`<div className="flex-1 ... flex items-start justify-center p-8">`), o
navegador não consegue resolver a cadeia de `width:100%` de forma estável.
Resultado observado ao vivo: a folha colapsa para uma largura mínima —
efetivamente o conteúdo mais estreito que cabe sem quebrar mais — e cada
palavra do corpo do laudo passa a ocupar uma linha própria. Consequências
visuais reproduzidas e fotografadas:

  - Texto sobreposto: "Achados" (do corpo do laudo) sobrepondo "Dr. Nome do
    Médico / CRM" (do rodapé), porque as alturas dos blocos dependem também
    da largura colapsada.
  - Um logo cujo campo "Largura (px)" eu alterei de 200 para 300 no painel
    esquerdo renderizou MINÚSCULO (~20px visíveis) e deslocado para dentro
    do texto "Data de nascimento:", em vez de aparecer no bloco do logo.
  - Nenhum erro no console do navegador — a quebra é inteiramente
    silenciosa, só visual.

Isto é a MESMA classe de bug que a Manus já documentou e corrigiu na
investigação do incidente de paginação de PDF ("folha de medição sem largura
física → medida como 0px"), mas aqui é uma ocorrência DIFERENTE, numa tela
diferente (o próprio Editor de Layout, não o pipeline de geração de PDF), e
está atualmente ao vivo em produção — não depende de nenhum branch revertido.

CORREÇÃO aplicada: envolver o SharedReportSheet do modo "real" no MESMO
`getCanvasOuterStyle(effectiveLayoutPrefs.pageSize)` que o modo "editor" já
usa corretamente, e trocar o style do SharedReportSheet para
`{ width: "100%", height: "100%" }` (a largura física passa a vir do
wrapper, não do componente) — paridade estrutural total entre os dois modos.
Ver client/src/pages/LayoutEditorPage.tsx, bloco `previewMode === "real"`.

4. MECANISMO DO PROBLEMA 2: legenda de texto fingindo ser uma terceira aba
------------------------------------------------------------------------------

Acima do canvas, o grupo de abas tinha esta estrutura:

    <div className="mb-3 flex items-center justify-center gap-3 flex-wrap">
      <div className="inline-flex ... shadow-sm">
        <button>Editar blocos</button>
        <button>Previa real</button>
      </div>
      <span className="text-xs text-gray-600">
        {previewMode === "real" ? "Visualizacao limpa da pagina" : "Modo de posicionamento"}
      </span>
    </div>

O `<span>` ficava na MESMA linha (mesmo flex container), com o MESMO
`gap-3` e o MESMO `text-xs text-gray-600` de tamanho/cor próximos aos
botões — visual e posicionalmente indistinguível de uma terceira opção de
aba. Mas é só texto: sem `onClick`, sem `cursor:pointer` (computado como
`auto`), sem handler algum. Confirmei isso tanto visualmente (cliques
repetidos não mudam nada) quanto lendo o DOM renderizado via JavaScript no
navegador (nenhum elemento com esse texto tem onclick/role=button, e
`getComputedStyle(el).cursor` retorna `"auto"`).

Isso é exatamente o "comando que não responde" que o Alessandro relatou:
alguém vê "Editar blocos | Previa real | Modo de posicionamento" e tenta
clicar na terceira, esperando entrar num modo dedicado de posicionamento —
e nada acontece, sem nenhum feedback de que aquilo nunca foi clicável.

Importante: um "modo de posicionamento" separado NÃO precisa ser criado.
Reposicionar os blocos já funciona hoje, por arrastar diretamente dentro de
"Editar blocos" — confirmei lendo `handlePointerDown`/`handlePointerMove`/
`handlePointerUp`, que usam Pointer Events reais (mouse, caneta e toque) e
estão corretamente implementados, incluindo os cálculos de
Bloqueio C (área útil real, não a folha inteira) já corrigidos numa rodada
anterior. O problema é só a legenda que sugere uma funcionalidade separada
que nunca existiu.

CORREÇÃO aplicada: mover a legenda para fora do grupo de botões, como um
`<p>` próprio, em itálico e entre parênteses, logo abaixo:

    <p className="mb-3 text-center text-[11px] italic text-gray-400">
      {previewMode === "real"
        ? "(visualização limpa da página, sem alças de arrastar)"
        : "(arraste os blocos diretamente nesta visualização para posicioná-los)"}
    </p>

Isso deixa claro, por contraste visual (itálico, cinza mais claro, fora da
"pílula" dos botões) e por conteúdo (parênteses, texto descritivo em vez de
nome de "modo"), que é uma descrição do estado atual — não uma opção
adicional.

5. MECANISMO DO PROBLEMA 3: "Resetar" destrutivo sem confirmação
------------------------------------------------------------------------------

O handler original:

    const handleReset = useCallback(() => {
      setPositions(DEFAULT_POSITIONS);
      setIsDirty(true);
      toast.info("Posições resetadas para o padrão.");
    }, []);

Um único clique no botão "Resetar" (sem diálogo de confirmação) descartava
TODAS as posições customizadas dos blocos — inclusive qualquer ajuste manual
feito minutos antes — sem chance de desfazer. Testei ao vivo: cliquei, e o
layout (que eu tinha alterado, e que já vinha com posições ajustadas para
essa unidade) pulou instantaneamente para o arranjo padrão (os dois logos
lado a lado no topo, blocos redistribuídos). O toast "Posições resetadas
para o padrão" aparece DEPOIS do fato consumado — não é uma confirmação,
é só um aviso do que já aconteceu.

Além disso, "Resetar" resetava só `positions` — os campos de largura/altura
de cada logo (`logos[].width/height`), a imagem de fundo e o rodapé não são
tocados. Isso é uma decisão de escopo razoável (evita perder uploads), mas
o rótulo genérico "Resetar" não deixava isso explícito, o que pode levar
alguém a esperar um reset total e se surpreender que logo/fundo/rodapé
continuam como estavam.

CORREÇÃO aplicada:

    const handleReset = useCallback(() => {
      if (!window.confirm("Resetar as posições de todos os blocos para o padrão? Isso descarta o posicionamento manual já ajustado (largura/altura dos logos, fundo e rodapé não são afetados). Esta ação não pode ser desfeita.")) {
        return;
      }
      setPositions(DEFAULT_POSITIONS);
      setIsDirty(true);
      toast.info("Posições dos blocos resetadas para o padrão (logos, fundo e rodapé não foram alterados).");
    }, []);

E o botão no header passou de "Resetar" para "Resetar posições", com
`title` explicando o escopo no hover.
