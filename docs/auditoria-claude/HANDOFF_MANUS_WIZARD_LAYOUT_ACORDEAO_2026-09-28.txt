4. OS 3 BUGS CONHECIDOS — CONFIRMADOS AO VIVO EM PRODUÇÃO HOJE, AGORA CORRIGIDOS
================================================================================

Estes 3 bugs já tinham sido encontrados, corrigidos e documentados em
28/09/2026 no branch claude/fix-layout-editor-previa-real-largura (handoff
docs/auditoria-claude/HANDOFF_MANUS_FIX_LAYOUT_EDITOR_PREVIA_REAL_2026-09-28.txt),
mas ESSE branch nunca foi mesclado em main. Antes de começar a reestruturação,
confirmei no código atual de origin/main (commit cdb1459) que os 3 bugs
continuam presentes — ou seja, quem estiver usando lauds.com.br/admin/layouts/*
hoje ainda tem esses problemas. Reapliquei as 3 correções por cima da
reestruturação em acordeão, para não reintroduzi-los na tela nova.

4.1. "Prévia real" colapsando para largura ~0
  Mecanismo: no modo previewMode==="real", o <SharedReportSheet> recebia
  style={{ width: "100%", maxWidth: `${paperWidthMmValue}mm`, minHeight: ... }}
  diretamente, sem nenhum ancestral com largura definida e sem aspectRatio. O
  elemento está dentro de uma coluna flex (o ternário previewMode==="editor" ?
  <>...</> : <>...</>), e sem base para resolver, o navegador colapsa maxWidth
  para a largura mínima do conteúdo — a folha praticamente sumia (só a altura
  mínima aparecia). getCanvasOuterStyle() (client/src/lib/layoutEditorAreaUtil.ts)
  já resolve isso no modo "editor" combinando width:100% + maxWidth + aspectRatio
  (o aspectRatio é o que dá ao flex item uma base para resolver o resto).
  Correção: envolvi o <SharedReportSheet> do modo real no mesmo
  <div style={getCanvasOuterStyle(effectiveLayoutPrefs.pageSize)}> e simplifiquei
  o style do próprio componente para {width:"100%", height:"100%"} — idêntico ao
  padrão já usado no modo editor.

4.2. Legenda das abas "Editar blocos" / "Prévia real" trocada e genérica
  Mecanismo: o texto era
    {previewMode === "real" ? "Visualizacao limpa da pagina" : "Modo de posicionamento"}
  — nenhuma das duas frases explica o que o modo realmente faz (a real não tem
  alças de arrastar; o de edição permite ajustar X/Y/Larg./Alt.), e ficava
  dentro da mesma linha flex dos botões de aba, competindo por espaço.
  Correção: texto próprio por modo, movido para um <p> dedicado abaixo dos
  botões:
    "Prévia real: mostra a página como sairá impressa, sem alças de arrastar."
    "Modo de posicionamento: arraste, redimensione e ajuste X/Y/Larg./Alt. dos blocos."

4.3. Botão "Resetar" sem confirmação
  Mecanismo: handleReset() chamava setPositions(DEFAULT_POSITIONS) direto no
  onClick — um clique acidental (o botão fica ao lado de "Salvar Layout" no
  cabeçalho) descartava todo o posicionamento customizado dos 8 blocos sem
  chance de desfazer em tela (só vira permanente depois de "Salvar", mas o
  estado visual já se perdia na hora).
  Correção: window.confirm() antes de resetar, com mensagem explicando que só é
  definitivo após salvar; rótulo do botão virou "Resetar posições" com title
  explicativo.

5. A NOVA REESTRUTURAÇÃO EM ACORDEÃO — MECANISMO
================================================================================

Estado novo: type PanelSection = "papel" | "identidade" | "blocos", useState
openSection (default "blocos", preservando o comportamento visual anterior de
a lista de blocos já vir visível), toggleSection() fecha se já estiver aberta.

Seção 1 — "Formato e margens" (NOVA):
  Botões A4/Letter chamando updatePreference("pageSize", size); 4 inputs
  numéricos (0-60, clamped) para marginTop/Right/Bottom/Left chamando
  updatePreference(field, valor). updatePreference() faz
  setLayoutPrefs(prev => ({...prev, [key]: value})) + setIsDirty(true).
  IMPORTANTE: antes desta correção, pageSize e as margens só podiam ser
  gravados chamando trpc.layouts.upsert diretamente (nenhuma tela do sistema
  os editava — LayoutEditorPage só LIA via effectiveLayoutPrefs;
  ReportEditorPage.tsx e PacsQueryPage.tsx também só leem, nunca escrevem).
  Confirmei que isso é seguro adicionar sem migration: handleSave() já envia
  `preferences: effectiveLayoutPrefs` no upsert (linha ~471, inalterada), e
  effectiveLayoutPrefs é `{...DEFAULT_LAYOUT_PREFERENCES, ...(layoutPrefs ?? {})}`
  — ou seja, os novos campos editados fluem para o mesmo payload que já era
  enviado, sem tocar em nenhuma outra parte do pipeline.

Seção 2 — "Logos, fundo e rodapé": as 3 seções antigas ("Logos da Unidade",
  "Fundo da Página", "Imagem de Rodapé") foram agrupadas sob um único header
  de acordeão. Nenhum handler, upload ou lógica interna foi alterado — só a
  visibilidade condicional por openSection === "identidade".

Seção 3 — "Blocos do Laudo": mesmo conteúdo de antes (lista dos 8 blocos com
  cor, toggle de visibilidade, e inputs X/Y/Larg./Alt. em %), agora atrás de
  openSection === "blocos" (aberta por padrão). Adicionei uma frase deixando
  explícito que a lista é só um atalho: "a lista abaixo é só um atalho para
  selecionar; a posição continua livre, sem grade". O clique num bloco na
  lista continua chamando setActiveBlock(block) (igual antes) — o que ativa o
  overlay de arrastar/redimensionar na folha (handlePointerDown/Move,
  inalterados). NÃO adicionei nenhum campo de posição "por clique" ou grade —
  o arraste livre em % (0-100, sobre a ÁREA ÚTIL real via usableAreaRef,
  correção já feita em 25/09 pelo Bloqueio C) continua sendo o único mecanismo
  de posicionamento.

BlockPosition (client/src/pages/LayoutEditorPage.tsx, tipo real) continua:
  { x: number; y: number; w: number; h: number; visible: boolean }
Sem "align" — esse campo existe só no protótipo Lovable à parte, não foi
trazido para cá (ver seção 3).
