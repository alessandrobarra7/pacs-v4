======================================================================
3. MECANISMO DO PROBLEMA
======================================================================

server/routers/units.ts, procedure `units.delete` (adminProcedure),
antes desta correção:

  delete: adminProcedure
    .input(z.object({ id: z.number() }))
    .mutation(async ({ input, ctx }) => {
      await deleteUnit(input.id);
      await createAuditLog({ ... action: 'DELETE_UNIT' ... });
      return { success: true };
    }),

E server/db.ts:

  export async function deleteUnit(id: number) {
    const db = await getDb();
    if (!db) throw new Error("Database not available");
    await db.delete(units).where(eq(units.id, id));
  }

Ou seja: um DELETE FROM units puro, sem transação e sem nenhuma
checagem de dependência. Uma consulta a information_schema.key_column_usage
confirma que praticamente nenhuma tabela do schema tem FK de verdade
para `units` (só algumas tabelas têm FK para outras entidades, nenhuma
delas cobre a relação com `units`), então o próprio MySQL nunca impediu
nem avisou sobre o DELETE — ele simplesmente deixa qualquer linha de
qualquer tabela com unit_id apontando para um registro inexistente.

Pelo menos ~25 tabelas no schema têm coluna unit_id (financial_responsible_units,
reports, studies_cache, billing_cycles, billing_visit_events,
user_unit_permissions, unit_exam_prices, model_layouts, contract_revenues,
unit_doctor_scales, etc.) — qualquer uma delas pode ficar órfã na
próxima exclusão de unidade com histórico, não só as que já
apareceram neste incidente.

Três telas do frontend chamam a mesma mutation `units.delete`:
client/src/pages/AdminPage.tsx, client/src/pages/Units.tsx e
client/src/pages/UnitsPage.tsx — todas com um simples
`window.confirm("Excluir...")`, sem nenhum aviso sobre dependências.
Como as três convergem para o mesmo endpoint, a correção no backend
cobre as três de uma vez, sem precisar mexer em nenhuma delas.

4. MECANISMO DA CORREÇÃO
======================================================================

server/db.ts ganhou uma nova função:

  export async function getUnitDependentRecords(unitId: number):
    Promise<{ table: string; count: number }[]>

Ela consulta information_schema.columns do banco atual (DATABASE())
para descobrir, dinamicamente, todas as tabelas com uma coluna
`unit_id` — exceto `units` (óbvio) e `audit_log` (trilha histórica de
auditoria, não é "dado vivo" preso à unidade; deve sobreviver à
exclusão). Para cada tabela encontrada, roda um
`SELECT COUNT(*) FROM <tabela> WHERE unit_id = ?` parametrizado e
retorna só as que têm count > 0.

Ser dinâmico (via information_schema) em vez de uma lista de tabelas
mantida à mão foi escolha deliberada: cobre automaticamente qualquer
tabela nova que uma migration futura adicione com coluna unit_id, sem
exigir que alguém lembre de atualizar uma lista neste arquivo.

server/routers/units.ts, procedure `units.delete`, agora chama essa
função ANTES de `deleteUnit`:

  const dependents = await getUnitDependentRecords(input.id);
  if (dependents.length > 0) {
    const resumo = dependents.map((d) => `${d.table} (${d.count})`).join(', ');
    throw new TRPCError({
      code: 'BAD_REQUEST',
      message: `Não é possível excluir esta unidade: existem registros
        vinculados em ${resumo}. Use "Desativar" em vez de "Excluir"
        para preservar o histórico.`,
    });
  }
  await deleteUnit(input.id);
  ...

Se existir qualquer dependência, a exclusão é recusada e nada é
tocado no banco (nem o DELETE, nem o audit log — o caller recebe o
erro TRPCError antes de qualquer efeito colateral).

A alternativa a "Excluir" já existe e não precisou ser criada: a
própria procedure `units.update` já aceita `isActive: z.boolean().optional()`,
e esse campo já é respeitado em várias leituras do sistema (ex.:
server/_core/index.ts linha ~918, server/routers/financeSimple.ts,
server/routers/admin.ts). Ou seja, "desativar uma unidade" (isActive=false)
já é um caminho seguro, testado e sem efeito colateral — só não era o
caminho que os três botões "Excluir" das telas oferecem.

Esta correção é deliberadamente conservadora: não tenta decidir
sozinha que "é seguro apagar um billing_cycle vazio mas não um report
assinado" — simplesmente bloqueia qualquer exclusão que deixaria
QUALQUER linha órfã, sem exceção, e deixa a decisão de como tratar
cada caso (migrar dado para outra unidade, arquivar, etc.) para uma
decisão humana explícita no momento em que ela acontecer, não para uma
lógica automática de limpeza que poderia apagar dado clínico por
engano.

6. O QUE FICOU FORA DO ESCOPO, DE PROPÓSITO
======================================================================

  - Nenhuma limpeza automática dos órfãos JÁ EXISTENTES em reports,
    billing_cycles e studies_cache (unidades 2 e 21) foi feita por
    este código. O dado de reports é clínico/legal real e não deve
    ser tocado por uma rotina automática; os de billing_cycles/
    studies_cache são de baixo risco mas não foram alterados porque
    não é esse o escopo desta correção (que é evitar NOVOS órfãos,
    não arquivar os antigos). Se o Alessandro ou a Manus decidirem
    que vale a pena arquivar/migrar esses 6 registros antigos, isso é
    uma decisão de produto separada, fora deste branch.
  - Não foi implementada nenhuma migration de schema (ex.: adicionar
    FK de verdade entre as ~25 tabelas e `units`). Isso resolveria o
    problema em uma camada mais baixa (o próprio MySQL recusando o
    DELETE com ON DELETE RESTRICT), mas é uma mudança de schema muito
    mais ampla, que exigiria auditar se alguma dessas 25 tabelas
    legitimamente pode ter unit_id órfão em algum fluxo válido antes
    de adicionar a constraint. Ficou fora deste branch por ser decisão
    de arquitetura maior, não um bugfix pontual.
  - As três telas do frontend (AdminPage.tsx, Units.tsx, UnitsPage.tsx)
    não foram alteradas. O guard no backend já cobre as três, e a
    mensagem de erro do TRPCError (que lista as tabelas e orienta a
    usar "Desativar") já chega ao usuário via toast.error nas telas
    que têm onError configurado (AdminPage.tsx e UnitsPage.tsx; Units.tsx
    usa toast.error(error.message) também). Se desejado, um ajuste de
    UX futuro poderia trocar o botão "Excluir" por "Desativar" como
    ação primária nessas telas, mas isso é decisão de produto/UX, não
    bugfix.
