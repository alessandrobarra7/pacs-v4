1. ORIGEM DA MUDANÇA

Você enviou REQUISITOS_FUNCIONALIDADE_RESPONSAVEL_FINANCEIRO_2026-09-17.txt
pedindo decisão de produto entre Opção A (um usuário = um responsável
financeiro ativo) e Opção B (um usuário pode acessar vários responsáveis,
com seleção explícita de contexto). Alessandro escolheu a Opção B — existe
necessidade operacional real de uma mesma conta administrar mais de um
responsável financeiro.

2. O QUE MUDOU

O schema já suportava isso (financial_responsible_users não tem unique
constraint em user_id). O problema era só a camada de aplicação:
getResponsibleIdForUser fazia .limit(1) em 13 lugares diferentes de
server/routers/financeSimple.ts, todos assumindo um único vínculo — o
mesmo tipo de resolução implícita e não determinística que causou o caso
da erica.

Dividi os 13 pontos em dois grupos:

Grupo 1 — checagens de autorização por unidade (assertCanAccessFinancialUnit,
assertCanManageExternalSalePrice, assertCanManageFinancialPrices,
getAuthorizedFinancialUnitIds, filtro de getDoctorStatement). Aqui a
pergunta é sempre "essa unidade pertence a algum dos MEUS responsáveis?" —
como uma unidade só pertence a um responsável ativo por vez, isso vira
simplesmente inArray() no lugar de eq(). Sem ambiguidade, sem precisar de
seleção de contexto.

Grupo 2 — telas que hoje mostram "o responsável" no singular sem receber
nenhum id explícito (myResponsavelSummary, getResponsible,
listUnitsForResponsible, getReportItems, getResponsibleSummary,
getMyResponsible, getResponsibleCycles, getResponsibleFullDashboard). Criei
resolveResponsibleContext(): financialResponsibleId explícito é validado
contra os vínculos reais do usuário; sem id explícito, resolve sozinho se
houver exatamente 1 vínculo (UX de sempre), retorna null se houver 0
(estado vazio, como sempre), e rejeita com BAD_REQUEST pedindo seleção se
houver mais de 1 — nunca escolhe "o primeiro" em silêncio.

Nova procedure listMyResponsibles retorna os responsáveis vinculados ao
usuário logado (id + nome), para montar um seletor de contexto.

3. FRONTEND

De todos os endpoints do Grupo 2, só myResponsavelSummary é chamado pelo
frontend hoje (client/src/pages/finance/FinanceMeuResponsavel.tsx — "Meu
Painel Financeiro"). Adicionei lá:
- um seletor de responsável no cabeçalho, visível só quando a conta tem
  mais de um vínculo ativo (com 0 ou 1 vínculo, tela idêntica a antes);
- enquanto há mais de um vínculo e nenhum selecionado, a tela mostra um
  aviso pedindo a seleção em vez de disparar a query (que rejeitaria com
  BAD_REQUEST).

Os outros endpoints do Grupo 2 (getResponsibleSummary, getMyResponsible,
getResponsibleCycles, getReportItems) não são chamados por nenhuma tela
hoje — corrigi por consistência e para uso futuro, mas isso não muda
nenhuma UI existente.

4. TESTES (server/audit-fixes-multi-responsavel-financeiro.test.ts)

- Grupo 1: usuário vinculado a 2 responsáveis, unidade pertence só ao
  segundo. Uso um spy no inArray real do drizzle-orm (mock parcial do
  módulo, preservando o resto) para provar que o código passou os dois ids
  pro inArray, não só um. Revertido de propósito para simular o bug antigo
  (pegar só o primeiro id), confirmado que o teste falha exatamente nessa
  asserção, revertido de volta.
- Grupo 2: 3 cenários — id não pertencente ao usuário (FORBIDDEN), 2
  vínculos sem id informado (BAD_REQUEST), 1 vínculo sem id (resolve
  sozinho), 0 vínculos (estado vazio). Os dois primeiros foram revertidos
  de propósito (simulando resolveResponsibleContext escolhendo o primeiro
  vínculo em silêncio), confirmado que ambos falham como esperado,
  revertidos de volta.
- server/financeSimple.test.ts: um teste estático pré-existente checava a
  string literal "ownResponsibleId !== input.responsibleId" (a checagem
  antiga de igualdade de um único id) dentro do código-fonte de
  getResponsibleFullDashboard. Atualizei a asserção para
  "!ownResponsibleIds.includes(input.responsibleId)" — mesma propriedade
  de segurança, generalizada pra array. Não é uma falha real, é um teste
  textual que precisava acompanhar a mudança intencional.
