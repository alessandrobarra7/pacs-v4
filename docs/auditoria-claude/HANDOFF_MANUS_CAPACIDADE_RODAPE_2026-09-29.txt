--------------------------------------------------------------------------------
3. A CORREÇÃO (item 1 do parecer: "contrato de capacidade")
--------------------------------------------------------------------------------

Em vez de aumentar um valor fixo de altura de bloco ou de imagem (que
não se adapta a blocos menores/maiores configurados por cada unidade
no editor de layout), implementei um contrato estrutural via CSS
flexbox, sem nenhuma medição em JavaScript:

a) SharedReportSheet.tsx: o wrapper externo do bloco footer passa de
   `alignItems:"center"` para `alignItems:"stretch"`, e o wrapper
   interno (que recebe o HTML do rodapé) ganha `height:"100%"`
   explícito. Isso transforma a altura do bloco footer numa altura
   DEFINIDA (não mais "auto") para fins de resolução de percentuais
   dos filhos — pré-requisito de CSS para o passo (b).

b) Em cada consumidor, `.doctor-footer` (ou `.signature`/`.stamp` no
   financeiro) vira um container flex em coluna com `height:100%`.
   Carimbo e assinatura ganham `flex:0 1 auto; min-height:0;`
   (mantendo os mesmos `max-height` de antes como limite SUPERIOR).
   Texto e linha divisória ganham `flex:0 0 auto` (tamanho fixo).

   O efeito: o motor de flexbox do próprio navegador redistribui o
   espaço disponível — se o conteúdo total (imagens + texto) excede a
   altura real do bloco, as imagens são as que encolhem primeiro
   (mantendo proporção via `object-fit:contain`, já existente), porque
   têm `min-height:0` e as outras não. O texto nunca fica menor (evita
   ficar ilegível), e `overflow:hidden` permanece como rede de
   segurança, mas deixa de ser o mecanismo principal.

Isso satisfaz o item 1 do parecer ("reservar altura suficiente... ou
posicionar fora de um container que recorte") por outro caminho: em vez
de reservar mais altura fixa, o conteúdo se adapta à altura real do
bloco, qualquer que seja ela.

--------------------------------------------------------------------------------
4. POR QUE NÃO É "overflow:visible ISOLADO" (item 2 do parecer)
--------------------------------------------------------------------------------

`overflow:hidden` continua presente em `.doctor-footer` e no bloco
footer — não foi removido. A diferença é que agora, na prática, ele
raramente precisa cortar nada, porque o conteúdo já se redimensiona
para caber. O único cenário residual onde `overflow:hidden` ainda
corta de verdade é descrito na seção 6 (fora de escopo).

6. FORA DE ESCOPO (limite real, não escondido)
--------------------------------------------------------------------------------

Se o admin configurar o bloco footer menor que o texto sozinho (nome +
CRM + data, sem espaço para nenhuma imagem), `overflow:hidden` ainda
corta — CSS `flex-shrink` reduz o tamanho da CAIXA de um item de texto,
não o tamanho da fonte, então um bloco extremamente pequeno ainda pode
cortar visualmente o texto. Isso é um cenário de configuração extrema
do admin no editor de layout, não o caso relatado (que era o TAMANHO
PADRÃO do bloco vs. conteúdo típico). Não implementei um limite mínimo
de altura no editor porque isso é uma decisão de produto (UX do editor
de layout), não uma correção de bug — sinalizo para você avaliar se
vale a pena um aviso na UI do editor.
