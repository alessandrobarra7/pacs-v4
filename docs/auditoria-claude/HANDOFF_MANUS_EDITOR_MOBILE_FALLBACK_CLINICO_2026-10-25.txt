A1. BLOQUEIO 1 — DADOS DO ESTUDO ANTERIOR AO TROCAR DE UID
    Concordo. Registro honesto: a falta de reset já existia antes do
    64bfa86 (o efeito nunca chamava setStudyInfo(null)); o commit anterior
    não a criou, mas também não a resolveu. Agora resolvido.
    Correção (ReportEditorPage.tsx):
      - O resultado da leitura é guardado JUNTO com o UID lido:
        studySession = { uid, info }. Derivados:
          studyInfo         = studySession.uid === studyUid ? info : null
          studyInfoResolved = studySession.uid === studyUid
        Isso é mais forte que setStudyInfo(null) no efeito: um efeito roda
        DEPOIS do render, então o primeiro render do UID B ainda mostraria
        A. Com o estado chaveado, A some já no primeiro render de B.
      - Efeito com reset determinístico ANTES de ler: examTitle =
        documentLabel da rota ou "", examNames = [], sectionBodies = [],
        previewHtml = "". Só depois lê e, se válido, preenche.
      - Nova função readStudySessionInfo (clinicalIdentityDisplay.ts):
        found | missing | invalid. Inválido = JSON quebrado, array,
        número, string, null ou storage que lança exceção. examNames só
        aceita strings.

A3. BLOQUEIO 3 — DATAS NEUTRAS INCONSISTENTES
    Concordo. Correção sobre o diagnóstico: formatDicomDate("   ") não
    devolve string vazia; devolve a própria string com espaços (o ramo
    "length === 8" falha e retorna dateStr). Por isso a folha mostrava um
    campo em branco. Efeito igual ao descrito; correção a mesma.
    Agora TODAS as saídas usam clinicalDateDisplay(formatDicomDate(x)):
      - nascimento e data do estudo na folha desktop simples;
      - nascimento e data do estudo na folha desktop multisseção;
      - nascimento no cartão mobile;
      - impressão/PDF (handlePrint). Achado extra: na impressão o
        nascimento ia CRU, sem formatDicomDate (AAAAMMDD no PDF).
    Valores brutos enviados ao backend não foram alterados.
