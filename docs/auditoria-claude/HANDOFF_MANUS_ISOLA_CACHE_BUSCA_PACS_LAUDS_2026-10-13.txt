BLOQUEIO 1 — regra de limpeza ampla demais ("qualquer chave pacs_")

A função original (`clearPacsLocalCache`) decidia o que apagar com base
em QUALQUER chave que começasse com o prefixo genérico "pacs_". Isso
funcionava para os dados clínicos, mas também apagava
`pacs_auto_download_unit_<unitId>` — uma preferência operacional do
usuário (se o PDF do laudo deve baixar automaticamente ao abrir um
estudo), que usa o mesmo prefixo mas não é dado de paciente. No
logout/troca de usuário, essa preferência era perdida sem necessidade.

Correção: `client/src/lib/pacsCacheIsolation.ts` agora usa uma allowlist
EXPLÍCITA de chaves clínicas — nunca um prefixo genérico, nunca
`localStorage.clear()`/`sessionStorage.clear()`. A lista final, confirmada
em código (grep real em PacsQueryPage.tsx, ReportEditorPage.tsx,
DicomViewerPage.tsx — nenhuma outra chave de storage existe nesses três
arquivos além das listadas):

  CLÍNICAS (removidas):
  - `pacs_selected_unit_id` (chave exata)
  - `pacs_query_results_unit_*` (prefixo)
  - `pacs_filter_unit_*` (prefixo)
  - `exam_label_*` (prefixo)
  - `study_*` (prefixo)
  - carimbo `pacs_cache_owner_user_id` — removido SÓ na função de logout
    explícito (`clearPacsClinicalCache`), nunca na função de
    troca-de-usuário (`purgeStaleCrossUserCacheIfNeeded`), que em vez
    disso sobrescreve o carimbo com o novo usuário depois de limpar.

  NÃO CLÍNICAS (preservadas, confirmadas em código em todo o client/src):
  - `pacs_auto_download_unit_*` — preferência operacional (mesmo prefixo
    "pacs_", mas não é dado clínico).
  - `pacs-layout-updated` — sinal de sincronização de layout entre abas
    (usa hífen, não underscore; sem paciente/laudo/UID).
  - `theme` (client/src/contexts/ThemeContext.tsx).
  - `sidebar-width` (client/src/components/DashboardLayout.tsx).
  - qualquer chave de outro módulo (ex.: financeiro).

  Função renomeada para deixar o escopo explícito no nome:
  `clearPacsLocalCache()` → `clearPacsClinicalCache()`.

BLOQUEIO 2 — AppHeader.tsx tinha logout próprio, nunca usava a rotina central

`client/src/components/AppHeader.tsx` é o header realmente renderizado
pela worklist do PACS (usado por `PacsQueryPage.tsx` e por
`AdminPage.tsx` — confirmado via grep). Ele tem seu PRÓPRIO
`handleLogout()`, com sua própria chamada a `trpc.auth.logout`, e sua
própria lógica de limpeza — que, antes desta correção, só removia chaves
`pacs_query_results*` de localStorage. Nunca chamava
`clearPacsLocalCache()`/`clearPacsClinicalCache()`. Ou seja: o logout que
o usuário realmente aciona ao clicar em "Sair" na tela de busca do PACS
não limpava filtros (sessionStorage), unidade selecionada, rótulos de
exame nem metadados de estudo — só uma fração do cache clínico.

(`client/src/_core/hooks/useAuth.ts`, que já chamava a função central
corretamente, é usado por `DashboardLayout.tsx`/`Home.tsx`/`App.tsx` —
outro caminho de logout, usado em outras telas, não na worklist do PACS.)

Correção: `AppHeader.tsx` agora importa `clearPacsClinicalCache` de
`@/lib/pacsCacheIsolation` e chama essa mesma função no `finally` do seu
`handleLogout`, antes do `window.location.href = "/login"` — sem duplicar
nenhuma lista de prefixos localmente. `useAuth.ts` foi só atualizado para
o novo nome da função (`clearPacsClinicalCache`), sem mudança de
comportamento.

`App.tsx` (ProtectedRoute), que já chamava
`purgeStaleCrossUserCacheIfNeeded(user.id)` corretamente antes de montar
qualquer página protegida, não precisou de nenhuma alteração — essa parte
da correção original já estava certa.

1. CONTEXTO / PEDIDO ORIGINAL

O Alessandro relatou uma suspeita: "sempre penso se a busca de exames funciona
corretamente para todos os usuários... tenho impressão que se logar de outro
usuário eu fico com a impressão que estou usando a busca de outros". Pedido:
investigar primeiro, sem presumir nada.

2. ACHADO (confirmado só por leitura de código, não suposição)

client/src/pages/PacsQueryPage.tsx (e as telas que a acompanham,
ReportEditorPage.tsx e DicomViewerPage.tsx) guardam resultados de busca,
filtros e metadados de estudo em localStorage/sessionStorage usando chaves
como:

  - pacs_query_results_unit_<unitId>
  - pacs_selected_unit_id
  - pacs_filter_unit_<unitId>
  - exam_label_<uid>
  - study_<uid>

Todas essas chaves são escopadas SÓ POR UNIDADE, nunca pelo usuário logado.
E o fluxo de logout (client/src/_core/hooks/useAuth.ts) nunca limpava nada
disso — só limpava o cache do React Query e redirecionava para /login.

Como queryResults é inicializado via useState(() => ...) (lazy initializer),
que roda de forma síncrona durante o render, ANTES de qualquer useEffect —
assim que a tela monta, o PRIMEIRO render já pinta os dados salvos da última
busca feita por QUALQUER usuário naquela mesma unidade, antes mesmo de uma
busca nova rodar no servidor.

Resultado prático: em um computador compartilhado (comum em postos de
trabalho de hospital), se o usuário A buscar exames na unidade X e sair sem
fechar o navegador — ou mesmo se clicar em "Sair" — o próximo usuário B que
logar e tiver acesso à mesma unidade X verá, por um instante (ou
indefinidamente, se não rodar nova busca), os resultados de busca do usuário
A: nomes de pacientes, exames, tudo.

IMPORTANTE — o que NÃO é o problema: o servidor (server/routers/pacs.ts)
autoriza corretamente cada requisição de busca por unit_id via
getUserUnitPermission/assertUnitPermission. Não há vazamento de dados entre
usuários no banco nem na API — o problema é 100% de higiene de cache no
navegador (cliente).

A suspeita do Alessandro era literalmente correta.

3. CORREÇÃO IMPLEMENTADA

Decisão de design: não reescrever o formato das chaves existentes (mudança
maior, toca 3 arquivos de tela com lógica delicada de cache). Em vez disso,
uma camada adicional, independente e de baixo risco:

a) client/src/lib/pacsCacheIsolation.ts (novo módulo)
   - clearPacsLocalCache(): limpa incondicionalmente toda chave com prefixo
     pacs_/exam_label_/study_ em localStorage e sessionStorage, mais o
     carimbo de dono. Chamada no logout.
   - purgeStaleCrossUserCacheIfNeeded(currentUserId): compara o usuário
     logado contra um carimbo salvo (pacs_cache_owner_user_id). Se não bate
     (ou não existe ainda), limpa tudo e grava o novo dono. Se já bate, não
     faz nada — preserva a conveniência original do cache para o MESMO
     usuário entre recargas de página.

b) client/src/_core/hooks/useAuth.ts — logout() agora chama
   clearPacsLocalCache() no finally, antes do reload para /login.

c) client/src/App.tsx — ProtectedRoute agora chama
   purgeStaleCrossUserCacheIfNeeded(user.id) ANTES de montar qualquer página
   protegida (antes do <Component>), usando um useRef para só rodar a
   checagem uma vez por troca de usuário. Isso cobre o caso mais comum na
   prática: alguém fecha a aba/navegador sem clicar em "Sair", e a próxima
   pessoa loga direto no mesmo navegador — nesse caso logout() nunca roda,
   mas o carimbo de dono detecta a troca de usuário do mesmo jeito, e
   crucialmente roda ANTES do primeiro render da página (ProtectedRoute
   decide se monta o filho ou não), evitando o "flash" de dado antigo que um
   useEffect dentro da própria PacsQueryPage chegaria tarde demais para
   evitar.
