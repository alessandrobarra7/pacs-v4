4. PENDÊNCIA — política de responsável financeiro inativo
------------------------------------------------------------
O relatório levantou a pergunta sem presumir a resposta, corretamente.
Perguntei ao Alessandro: decisão foi POLÍTICA DE BLOQUEIO TOTAL — um
responsável financeiro inativo não pode receber novos usuários, nem
permitir leitura financeira, alteração de preço ou de ciclo pelos
usuários vinculados a ele. O vínculo em financial_responsible_users NÃO é
apagado quando o responsável é desativado; ele só para de contar pra
autorização enquanto isActive=false.

Implementação: o ponto de menor superfície e maior cobertura é
server/db.ts — getResponsibleIdForUser e getResponsibleIdsForUser são as
duas funções que praticamente toda checagem de autorização financeira
usa pra resolver o(s) responsável(is) de um usuário (assertCanAccessFinancialUnit,
assertCanManageFinancialPrices, resolveResponsibleContext,
myResponsavelSummary, etc.). As duas agora fazem innerJoin com
financial_responsibles e filtram isActive=true — o bloqueio cascateia
para todo o módulo sem precisar repetir a checagem em cada procedure
isolada. Além disso, financeSimple.linkUser passou a recusar conceder
acesso NOVO a um responsável já inativo (antes só validava que a CONTA de
login está ativa, nunca o responsável).

Cobertura de teste: adicionado 1 teste em
server/audit-fixes-gestao-usuarios-responsavel.test.ts (linkUser rejeita
responsável inativo). Os 4 mocks existentes de getFinancialResponsibleById
nesse arquivo foram corrigidos para incluir isActive:true (senão o novo
guard os teria quebrado com falso-positivo, já que undefined é falsy).

Limitação honesta desta cobertura: getResponsibleIdForUser/
getResponsibleIdsForUser chamam getDb() dentro do PRÓPRIO server/db.ts —
não é possível mockar getDb via vi.mock("./db", ...) e ainda executar a
implementação real dessas duas funções no mesmo teste (auto-referência
de módulo; tentei, confirmei o erro "Database not available" quando a
implementação real tenta usar um getDb não mockado, documentado
anteriormente neste projeto). Ou seja: o innerJoin+isActive foi verificado
por leitura de código e por tsc (a query é type-safe contra o schema), e
o efeito em cascata na autorização é testado na camada de router (que já
mockava essas duas funções como dependência externa, fronteira válida
pra mock). Mas a query SQL em si, gerada por essas duas funções, não tem
teste automatizado isolado no meu ambiente. Peço que valide especificamente
este ponto contra um banco de sandbox real: um usuário vinculado só a um
responsável inativo deve efetivamente perder acesso a myFinanceiro,
myModalityPrices, myResponsavelSummary etc.
