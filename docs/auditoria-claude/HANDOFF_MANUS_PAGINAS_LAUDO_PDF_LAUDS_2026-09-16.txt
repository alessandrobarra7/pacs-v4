confirmando com evidência de código (não por suposição) que o sistema tem
CINCO implementações independentes que produzem a mesma "folha" do laudo:

  1. client/src/components/ReportDocument.tsx — o que o médico VÊ na tela
     ao escrever/revisar (WYSIWYG). Único ponto que já fazia certo: usa
     `{...DEFAULT_LAYOUT_PREFERENCES, ...preferences}` (importa a
     constante canônica de shared/types.ts). NÃO ALTERADO nesta branch —
     já estava correto, serviu de referência para as outras 4.

  2. client/src/pages/ReportEditorPage.tsx → handlePrint() — impressão
     oficial do laudo (o fluxo usado ao assinar/imprimir de verdade).
     CORRIGIDO no commit 1.

  3. client/src/pages/ReportEditorPage.tsx → handleFinancialPdfDownload()
     — download de PDF ativado por `?financialView=1` (usado a partir do
     módulo financeiro para o médico baixar cópia do próprio laudo
     assinado). CORRIGIDO no commit 1 (mesmo arquivo do item 2).

  4. client/src/pages/PacsQueryPage.tsx — impressão rápida a partir da
     lista de exames (o código já tinha um comentário `/* SYNC
     ReportEditorPage */`, evidenciando que era cópia manual do bloco do

  5. client/src/lib/financialReportPdfDownload.ts (usado em
     client/src/pages/finance/FinanceMeuFinanceiro.tsx) — outro download
     de PDF do módulo financeiro, para o "meu financeiro" do médico.
     CORRIGIDO no commit 3.

A fonte de verdade canônica é `shared/types.ts`:

    ...
    marginTop: 20, marginRight: 25, marginBottom: 25, marginLeft: 25,
    ...
    pageSize: "A4",

Com o comentário no próprio arquivo: "Valores padrão do layout — NÃO

branch, SÓ ReportDocument.tsx (item 1) realmente importava e usava essa
constante; os itens 2, 3, 4 e 5 reimplementavam fallbacks numéricos à mão,
e já tinham divergido entre si (ver evidência exata abaixo).

Vale registrar o que JÁ estava bem-feito, para não dar a entender que tudo

1. server/../client/src/pages/ReportEditorPage.tsx
   fix(report-editor): unificar margens/pageSize com
   DEFAULT_LAYOUT_PREFERENCES
=============================================================================
Duas correções distintas neste arquivo/commit:

1.1) handlePrint() — ANTES:
  const lMT = layoutPrefs?.marginTop ?? 20;
  const lMB = (layoutPrefs?.marginBottom ?? 20) + footerReservedMm;
  const lML = layoutPrefs?.marginLeft ?? 18;
  const lMR = layoutPrefs?.marginRight ?? 18;
  ...
  const pageSize = (layoutPrefs as any)?.pageSize ?? 'A4';

  MECANISMO DO PROBLEMA: os fallbacks (20/20/18/18) eram valores
  inventados neste arquivo, diferentes do canônico em
  DEFAULT_LAYOUT_PREFERENCES (20/25/25/25). Isso só se manifesta
  visivelmente quando `layoutPrefs` está incompleto ou ausente — por
  exemplo, uma unidade que nunca configurou layout próprio (getByUnit
  retorna null nesse caso) ou um registro legado salvo antes de algum
  campo existir no schema. Nesse cenário, o laudo que o médico via na
  tela (ReportDocument.tsx, com margem esquerda/direita 25mm) saía
  impresso com margem esquerda/direita 18mm — o documento impresso não
  batia com o que foi revisado na tela antes de assinar.

  MECANISMO DA CORREÇÃO: adicionado
  `const effectivePrefs: LayoutPreferences = { ...DEFAULT_LAYOUT_PREFERENCES, ...(layoutPrefs ?? {}) };`
  logo antes do bloco de margens, e todos os campos (lMT, lMB, lML, lMR,
  rawFont, lSize, lLine, lBorderColor, pageSize) passaram a ler de
  `effectivePrefs` em vez de repetir `layoutPrefs?.campo ?? valor` campo a
  campo. `DEFAULT_LAYOUT_PREFERENCES` foi importado de shared/types.ts
  (mesmo import que ReportDocument.tsx já usa).

1.2) handleFinancialPdfDownload() — ANTES:
  const pdf = new jsPDF("p", "mm", "a4");

  MECANISMO DO PROBLEMA: formato fixo em "a4", sem NENHUMA leitura de
  layoutPrefs.pageSize. Diferente do item 1.1 (que só falha em
  layoutPrefs incompleto), este é INCONDICIONAL: mesmo com layoutPrefs
  totalmente preenchido e pageSize="Letter" explícito, o PDF baixado por
  este botão sempre saía A4 — o mesmo laudo, Letter na impressão oficial
  (handlePrint) e A4 neste download.

  MECANISMO DA CORREÇÃO:
  const effectivePageSize = (layoutPrefs?.pageSize ?? DEFAULT_LAYOUT_PREFERENCES.pageSize) as "A4" | "Letter";
  const pdf = new jsPDF("p", "mm", effectivePageSize.toLowerCase() as "a4" | "letter");
  `layoutPrefs` foi adicionado às dependências do useCallback (antes só
  tinha `[patientName]`).

ambos os arquivos, não só nos valores). Fica registrado como sugestão

3. client/src/lib/financialReportPdfDownload.ts
   fix(finance-pdf): ler margens configuradas do layout em vez de
   hardcoded
=============================================================================
ANTES:
  const pageSize = preferences.pageSize === "Letter" ? "Letter" : "A4";
  ...
  .print-page { ...padding:16mm 18mm 30mm...  }

MECANISMO DO PROBLEMA: diferente dos outros dois arquivos, este nem
tentava ler marginTop/marginBottom/marginLeft/marginRight das
preferências — o CSS usava um padding fixo (`16mm 18mm 30mm` — top 16mm,
laterais 18mm, bottom 30mm, na notação abreviada de 3 valores) para
QUALQUER unidade, incondicionalmente. Se um administrador configurasse,
por exemplo, marginTop=40mm (papel timbrado com cabeçalho grande), essa
configuração era simplesmente ignorada aqui — o laudo baixado por este
caminho sempre usava 16mm no topo, batendo o cabeçalho por cima do papel
timbrado.

MECANISMO DA CORREÇÃO:
  const effPrefs = { ...DEFAULT_LAYOUT_PREFERENCES, ...preferences };
  ...
  const marginTop = Number(effPrefs.marginTop);
  const marginRight = Number(effPrefs.marginRight);
  const marginBottom = Number(effPrefs.marginBottom) + footerReservedMm; // +30mm se houver imagem de rodapé, mesmo padrão dos outros dois arquivos
  const marginLeft = Number(effPrefs.marginLeft);
  ...
  .print-page { ...padding:${marginTop}mm ${marginRight}mm ${marginBottom}mm ${marginLeft}mm...  }
`DEFAULT_LAYOUT_PREFERENCES` foi importado de "../../../shared/types".
pageFontFamily/fontSize/lineHeight, que já eram lidos corretamente antes,
passaram a vir do mesmo `effPrefs` por consistência (não havia bug nesses
três campos, só reorganização para uma única fonte).
